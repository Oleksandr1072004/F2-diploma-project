| Тип архітектури | EDA + CQRS + Saga | Моноліт | Клієнт-серверна | Товстий клієнт |

****Постановка задачі та формування вимог (модель To-Be)****

**1. Опис концептуальної моделі To-Be**

Цільовий стан системи (To-Be) передбачає трансформацію локальних синхронних процесів діагностики у розподілену подієво-керовану архітектуру (Event-Driven Architecture). У межах запропонованої моделі мобільний клієнт (Flutter) виступає джерелом телеметричних даних, які через REST API транслюються на серверну частину (FastAPI) та публікуються у брокер повідомлень Apache Kafka. Це дозволяє ліквідувати вузькі місця, пов'язані з блокуванням потоків під час очікування відповіді від OBD-II адаптера. Обробка DTC-кодів, генерація PDF-звітів та відправка сповіщень у Telegram-бот реалізуються асинхронно через консюмерів Kafka. Застосування патерну CQRS забезпечує розділення операцій запису (PostgreSQL) та читання (Redis), що знижує Latency при запитах історії. Для гарантії цілісності даних при розподілених транзакціях впроваджується патерн Saga з компенсуючими діями. Відмовостійкість забезпечується патернами Circuit Breaker та Retry із експоненційною затримкою.

**2. Функціональні вимоги (Core Features)**

- **Модуль збору телеметрії (Mobile Client):** зчитувати параметри OBD-II (RPM, швидкість, температура, напруга) через Bluetooth із частотою дискретизації ≥ 10 Гц; передавати дані на сервер через REST API.
- **Модуль обробки подій (Backend):** публікувати телеметричні події до Apache Kafka; забезпечувати асинхронну обробку черг із гарантією доставки (at-least-once).
- **Модуль декодування DTC:** виконувати семантичний аналіз кодів помилок із прив'язкою до внутрішньої бази знань та збереженням результатів у PostgreSQL.
- **Модуль управління станом (CQRS):** реалізовувати розділення write-model (PostgreSQL) та read-model (Redis) для операцій з історією діагностик.
- **Модуль генерації звітів:** формувати PDF-звіти з агрегованою історією діагностик, параметрами датчиків та фотографіями стану оптики.
- **Модуль Telegram-бота (aiogram):** надавати користувачу інтерфейс для запиту історії діагностик, розшифровки DTC-кодів та отримання ШІ-консультацій.
- **Модуль Observability:** експортувати метрики (Prometheus) та розподілені трейси (Jaeger) через OpenTelemetry для моніторингу стану системи.
- **Модуль управління доступом:** реалізовувати автентифікацію та авторизацію користувачів на базі OAuth 2.0 / OIDC з використанням підписаних JWT-токенів.

**3. Нефункціональні вимоги (NFRs)**

| **Категорія** | **Вимірювана метрика** |

**4. Постановка задачі**

Таким чином, метою кваліфікаційної роботи є проєктування та розробка подієво-керованої розподіленої екосистеми для автомобільної діагностики, що забезпечує асинхронну обробку телеметричних даних, централізоване збереження історії діагностик, автоматизовану генерацію звітів та інтеграцію з Telegram-ботом. Система повинна забезпечувати Latency API на p95 ≤ 200 мс при навантаженні 500 RPS, відповідати стандартам OWASP ASVS Level 2 та GDPR, а також реалізовувати контур Observability для моніторингу деградацій та Fault Tolerance на рівні SLA 99.5%.

*Здійснено верифікацію згенерованих вимог. Абстрактні формулювання на кшталт «система має працювати швидко» замінено на конкретні метрики (Latency p95 ≤ 200 мс, 500 RPS). Для NFRs надійності додано цільовий показник SLA 99.5% та вимоги до RPO/RTO.*
