# ADR-001: Вибір Apache Kafka як брокера повідомлень

## Status
Proposed

## Context
Система AutoSpark Pro потребує асинхронної обробки подій діагностики (DTC-коди, телеметрія) з підтримкою високої пропускної здатності (≥ 1000 подій/с) та можливістю повторного читання подій для генерації звітів. Обмеження SRS: Latency p95 ≤ 200 мс, Fault Tolerance, горизонтальне масштабування.

## Alternatives
1. **Apache Kafka:** Розподілений лог-орієнтований брокер. Підтримує персистентність подій, повторне читання (replay), горизонтальне масштабування через партиції.
2. **RabbitMQ:** Черга повідомлень із підтримкою AMQP. Легший у налаштуванні, але менш ефективний для високих навантажень та повторного читання.

## Decision
Обрано **Apache Kafka** з таких причин:
- Підтримка персистентного логу подій (replay) для генерації звітів.
- Горизонтальне масштабування через партиції (≥ 1000 подій/с).
- Інтеграція з FastAPI через `aiokafka`.
- Висока Fault Tolerance через реплікацію партицій.

## Consequences
**Позитивні:**
- Висока пропускна здатність та Fault Tolerance.
- Можливість replay подій для аналітики.

**Негативні:**
- Ускладнення інфраструктури (Zookeeper/KRaft).
- Вищий поріг входження для команди.
- FinOps: Kafka вимагає більше ресурсів, ніж RabbitMQ.
