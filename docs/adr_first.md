# ADR-001: Вибір Apache Kafka як брокера повідомлень

## Status
Proposed

## Context
Система AutoSpark Pro потребує асинхронної обробки подій діагностики (DTC-коди, телеметрія) з підтримкою високої пропускної здатності (≥ 1000 подій/с) та можливістю повторного читання подій для генерації звітів. Обмеження SRS: Latency p95 ≤ 200 мс, Fault Tolerance, горизонтальне масштабування.

## Alternatives
1. **Apache Kafka:** Розподілений лог-орієнтований брокер. Підтримує персистентність подій, повторне читання (replay), горизонтальне масштабування через партиції.
2. **RabbitMQ:** Черга повідомлень із підтримкою AMQP. Легший у налаштуванні, але менш ефективний для високих навантажень та повторного читання.

## Decision
Обрано **Apache Kafka** з таких причин:
- Підтримка персистентного логу подій (replay) для генерації звітів.
- Горизонтальне масштабування через партиції (≥ 1000 подій/с).
- Інтеграція з FastAPI через `aiokafka`.
- Висока Fault Tolerance через реплікацію партицій.

## Consequences
**Позитивні:**
- Висока пропускна здатність та Fault Tolerance.
- Можливість replay подій для аналітики.

**Негативні:**
- Ускладнення інфраструктури (Zookeeper/KRaft).
- Вищий поріг входження для команди.
- FinOps: Kafka вимагає більше ресурсів, ніж RabbitMQ.



# ADR-001: Вибір Apache Kafka як брокера повідомлень

## Status
Approved

## Context
Система AutoSpark Pro потребує асинхронної обробки подій діагностики з підтримкою довготривалого зберігання (Event Log) для можливості повторного читання (replay) при генерації звітів. Обмеження SRS: гарантована доставка (at-least-once), Fault Tolerance, автентифікація SASL/SCRAM.

## Alternatives
1. **Apache Kafka:** Розподілений лог-орієнтований брокер. Забезпечує персистентність подій на диску, replay, горизонтальне масштабування.
2. **RabbitMQ:** Черга повідомлень (AMQP). Ефективний для Task Queue, але не має нативного довготривалого логу для replay.
3. **Redis Streams:** Легковаговий брокер на базі Redis. Підходить для кешування, але обмежений обсягом RAM, що унеможливлює довготривале зберігання історії.

## Decision
Обрано **Apache Kafka**. Незважаючи на вищу операційну складність, Kafka є єдиним рішенням, що задовольняє вимогу SRS щодо довготривалого зберігання подій (Event Sourcing) та replay для генерації звітів.

## Consequences
**Позитивні:**
- Гарантована доставка (at-least-once) та можливість replay подій.
- Висока Fault Tolerance через реплікацію.
- Підтримка патерну Transactional Outbox.

**Негативні:**
- Ускладнення інфраструктури (потреба в KRaft-контролері, налаштування SASL/SCRAM).
- Необхідність реалізації Dead Letter Queue (DLQ) для обробки помилок, що збільшує технічний борг.
- Ризик vendor lock-in при використанні Confluent Schema Registry.
- FinOps: вищі вимоги до RAM та дискового простору порівняно з RabbitMQ.
